# 数据库迁移方案说明（SQLite → PostgreSQL + Alembic）

## 1. 文档目的

给出“法律 AI”项目从 SQLite 升级到 PostgreSQL，并从 `create_all` 过渡到 Alembic 的正式迁移路线，用于实施前评审、过程执行与答辩讲解。

## 2. 为什么必须迁移

### 2.1 SQLite 的当前作用

SQLite 在当前阶段承担了原型数据库角色，优点是：
- 零配置
- 启动快
- 适合本地开发和 MVP 验证

### 2.2 SQLite 不适合正式交付的原因

- 不利于多环境部署
- 并发能力有限
- schema 演进管理薄弱
- 数据运维能力不足
- 不适合作为课程/项目中的“企业级交付”数据底座展示

### 2.3 为什么选择 PostgreSQL

- 开源成熟、生态稳定
- 支持更规范的关系模型与索引能力
- 更适合承载 JSON / JSONB
- 更适合与 Alembic、Docker、CI/CD 配合
- 更符合企业级项目的常规技术路线

### 2.4 为什么引入 Alembic

当前项目使用：
- `Base.metadata.create_all()` 初始化表
- `ensure_legacy_schema()` 运行时修补历史字段

这种方式的问题是：
- schema 历史不可追踪
- 变更不可审查
- 团队成员间难同步
- 生产环境难保证一致性

Alembic 的价值是：
- 每一次结构变更有版本记录
- 迁移过程可审查、可执行、可回滚
- 适合 dev/test/prod 多环境统一管理

## 3. 当前数据库现状

### 当前连接方式
- 连接串来自 `DATABASE_URL`
- 默认值：SQLite
- ORM：SQLAlchemy Async

### 当前表结构
- `users`
- `analyses`
- `comparisons`
- `chat_sessions`
- `chat_messages`
- `favorites`

### 当前特殊情况
- `comparisons` 表存在 legacy 兼容补丁逻辑
- 收藏去重目前只靠应用层判断
- 尚无数据库迁移目录

## 4. 迁移目标

本次迁移的目标是：

1. 将正式环境数据库切换为 PostgreSQL
2. 引入 Alembic 作为唯一 schema 演进机制
3. 保持现有 ORM 和业务模型基本不变
4. 为第 4 周认证鉴权改造预留数据基础
5. 为第 7-8 周测试和部署建设提供稳定底座

## 5. 推荐迁移原则

### 原则 1：先正规化，再扩展
不要在迁移周同时做大量新字段设计或功能重构。

### 原则 2：先建干净目标库，再决定是否搬历史数据
先把 PostgreSQL schema 跑通，再决定历史数据要不要搬。

### 原则 3：迁移要服务交付，不追求炫技
对当前项目来说，最合理的是“可解释、可执行、可验证”的迁移路线。

## 6. 推荐实施路线

### 第一步：引入 Alembic 基础目录
建议新增：
- `alembic.ini`
- `alembic/`
- `alembic/env.py`
- `alembic/versions/`

### 第二步：让 Alembic 识别 SQLAlchemy 模型
目标：
- 让 Alembic 使用当前 `Base.metadata`
- 能够生成第一版初始化迁移

### 第三步：生成初始化迁移
目标：
- 根据当前 ORM 模型生成第一版 schema
- 初始化版本只描述“目标结构”，不再依赖运行时补丁

### 第四步：准备 PostgreSQL 环境
准备内容：
- PostgreSQL 数据库实例
- 新的 `DATABASE_URL`
- 独立测试数据库（可选但推荐）

### 第五步：执行迁移
在 PostgreSQL 环境中执行 Alembic upgrade，创建正式表结构。

### 第六步：决定历史数据策略
两种路线：

#### 路线 A：冷启动
- 不导入旧 SQLite 历史数据
- 新库只创建 schema
- 最适合答辩、验收、演示环境

#### 路线 B：迁移历史数据
- 从 SQLite 导出当前业务记录
- 按表顺序导入 PostgreSQL
- 导入后校验总数和关系一致性

## 7. 数据迁移顺序建议

若采用带历史数据迁移，推荐顺序：

1. `users`
2. `analyses`
3. `comparisons`
4. `chat_sessions`
5. `chat_messages`
6. `favorites`

原因：
- 先迁移主表用户
- 再迁移依赖用户的业务表
- 最后迁移依赖会话的消息表

## 8. Alembic 使用规则建议

### 8.1 初始化命令思路
- 初始化 Alembic 目录
- 配置 `env.py`
- 生成初始 revision
- 执行 upgrade

### 8.2 后续 schema 变更规则
后续所有数据库结构修改必须通过 Alembic 完成，包括：
- 新字段
- 索引
- 唯一约束
- 外键调整
- 表重命名/字段重命名

### 8.3 禁止事项
- 禁止继续只依赖 `create_all()` 演进正式 schema
- 禁止继续写运行时 `ALTER TABLE` 补丁作为长期方案
- 禁止多人各自手动改数据库结构而不提交 migration

## 9. 风险点与应对

### 风险 1：SQLite 与 PostgreSQL 行为差异
可能影响：
- JSON 字段表现
- 时间字段兼容性
- 约束严格度

应对：
- 在测试环境先跑一遍 PostgreSQL
- 以 Alembic 创建的新库为准做验证

### 风险 2：历史数据脏数据
可能影响：
- 匿名用户与正式用户混杂
- 收藏重复
- 冗余计数字段不一致

应对：
- 迁移前做一次数据体检
- 必要时允许“只迁 schema，不迁历史业务数据”

### 风险 3：第 4 周认证改造与用户表耦合
可能影响：
- 登录方式正式化后，旧匿名数据与新用户体系融合复杂

应对：
- 第 3 周尽量不提前过度设计用户字段
- 只预留扩展空间，把认证字段设计集中放在第 4 周

## 10. 验证方案

迁移完成后至少验证以下内容：

1. 后端能基于 PostgreSQL 启动
2. 所有核心表正确创建
3. 文档分析链路可写入 `analyses`
4. 文档对比链路可写入 `comparisons`
5. 聊天会话和消息可写入 `chat_sessions` / `chat_messages`
6. 收藏写入与查询正常
7. Alembic 当前版本与数据库版本一致

## 11. 回退思路

### 回退策略 1：环境级回退
如果 PostgreSQL 接入失败，可临时切回 SQLite 继续开发，但仅限过渡。

### 回退策略 2：数据级回退
保留旧 SQLite 文件备份，在带历史迁移失败时可回到原库重新验证导出逻辑。

### 回退策略 3：执行节奏回退
若带历史数据迁移复杂度过高，可先交付“PostgreSQL 空库初始化 + 新环境可运行”，把历史数据迁移降为补充项。

## 12. 最推荐的落地方案

对于当前项目，最推荐的第 3 周路线是：

1. 引入 Alembic
2. 以当前模型生成 PostgreSQL 初始化 schema
3. 建立新的 PostgreSQL 启动方式
4. 先完成“冷启动可运行”
5. 历史 SQLite 数据迁移作为可选增强

原因：
- 风险最低
- 最符合三个月交付窗口
- 最便于在答辩中清楚解释
- 不会阻塞第 4 周认证改造

## 13. 结论

第 3 周数据库升级的关键，不是把数据库“换一下”这么简单，而是要把整个数据层从“原型期的临时方案”升级为“正式交付期的可治理方案”。

因此本周真正的成果标准应该是：
- PostgreSQL 成为正式目标数据库
- Alembic 成为唯一迁移机制
- 迁移路线可解释、可执行、可验证
- 第 4 周之后的数据改造不再被底层 schema 管理拖后腿
