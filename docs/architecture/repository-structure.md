# 目录结构与模块职责说明

## 1. 文档目的

本说明用于帮助开发者、答辩老师、项目协作者快速理解当前仓库的目录结构、模块边界，以及在第一版“系统门户 + 自注册 + user/admin”方案下的推荐演进方向。

## 2. 仓库根目录概览

| 路径 | 用途 | 当前状态 |
|---|---|---|
| `README.md` | 项目总说明 | 已存在，需持续与正式方案保持一致 |
| `backend/` | 后端代码与运行资源 | 核心业务主目录 |
| `frontend/` | 前端静态页面资源 | 当前单页应用前端 |
| `docs/` | 交付文档与计划文档 | 已进入系统化建设阶段 |
| `.venv/` | 项目虚拟环境 | 本地环境目录，不应提交 |

## 3. 后端目录说明

### 3.1 `backend/app/`

后端主代码目录。

| 路径 | 职责 |
|---|---|
| `backend/app/main.py` | FastAPI 应用入口、路由注册、静态资源挂载、健康检查 |
| `backend/app/config.py` | 读取环境变量并形成集中配置对象 |
| `backend/app/api/` | API 路由层，负责对外暴露 HTTP 接口 |
| `backend/app/core/` | 核心业务能力层，负责法条库、文档解析、OCR、AI 分析等 |
| `backend/app/models/` | 数据模型层，包含 SQLAlchemy 模型和 Pydantic schema |

### 3.2 `backend/app/api/`

当前 API 已按业务主题拆分，边界相对清晰。第一版建议在现有基础上继续收口，而不是推翻重做。

| 文件 | 职责 |
|---|---|
| `search.py` | 法条搜索与相似检索 |
| `document.py` | 文档分析、流式分析、文档对比、结果查询 |
| `chat.py` | 聊天会话、消息发送、流式问答、会话删除 |
| `user.py` | 注册、登录、当前用户、历史、收藏、工作台 |
| `template.py` | 模板列表、分类、详情 |
| `deps.py` | 依赖注入、当前用户解析、角色校验 |
| `admin.py`（建议新增） | 系统状态、用户管理、记录管理 |

第一版接口分区建议：
- 公共接口：注册、登录、门户/帮助所需只读内容
- 用户接口：工作台、历史、收藏、分析、对比、聊天
- 管理接口：系统状态、用户治理、记录查看

### 3.3 `backend/app/core/`

当前核心业务层是项目最有价值的能力层，应尽量保持稳定，不做无必要大改。

| 文件 | 职责 |
|---|---|
| `legal_db.py` | 法条数据加载与检索 |
| `vector_store.py` | 向量检索能力 |
| `document_parser.py` | 文档解析总入口 |
| `document_service.py` | 文档/OCR 相关装配入口 |
| `ocr.py` | OCR 公共导出 |
| `ocr_base.py` | OCR 抽象接口 |
| `ocr_paddle.py` | PaddleOCR 主引擎 |
| `ocr_tesseract.py` | Tesseract 回退引擎 |
| `ocr_router.py` | OCR 主备路由 |
| `ocr_quality.py` | OCR 质量判定逻辑 |
| `ai_analyzer.py` | AI 合同分析、问答、对比主能力 |

### 3.4 `backend/app/models/`

| 文件 | 职责 |
|---|---|
| `database.py` | SQLAlchemy 异步引擎、ORM 模型、数据库初始化 |
| `schemas.py` | Pydantic 数据结构定义 |

第一版数据层重点：
- `users` 模型从匿名/openid 风格切换为正式账号密码模型
- 增加 `role`、`status`、`last_login_at` 等字段
- 为 `admin` 管理查询提供可聚合的数据结构

### 3.5 `backend/data/`

存放静态业务数据。

| 文件 | 用途 |
|---|---|
| `civil_law.json` | 民法典数据 |
| `criminal_law.json` | 刑法数据 |
| `templates.json` | 合同模板数据 |

### 3.6 `backend/uploads/`

运行时上传文件目录。

当前问题：
- 已混入运行数据
- 缺少按环境隔离策略
- 缺少统一清理规则

第一版建议：
- 保留目录位置不变
- 增加文件类型白名单和生命周期说明
- 明确生产环境应挂载为独立持久卷或独立目录

### 3.7 `backend/requirements.txt`

后端依赖清单，继续作为单体后端依赖入口。

## 4. 前端目录说明

### 4.1 `frontend/`

当前前端是原生 HTML/CSS/JavaScript 单页应用。

| 路径 | 职责 |
|---|---|
| `frontend/index.html` | 当前页面入口 |
| `frontend/css/style.css` | 全局样式 |
| `frontend/js/app.js` | 前端主逻辑：状态、请求、页面交互、展示逻辑 |

### 4.2 第一版前端推荐分区

虽然本期不做 React 重构，但建议在现有前端基础上完成“页面结构正式化”。

建议视图分区：
- 公共区：门户、登录、注册、帮助
- 用户区：工作台、搜索、分析、对比、问答、历史、收藏
- 管理区：系统状态、用户管理、记录管理

### 4.3 第一版前端推荐模块拆分

在不引入新框架的前提下，建议逐步把 `frontend/js/app.js` 拆分为：
- `api.js`：统一接口请求
- `auth.js`：登录、注册、登出、当前用户状态
- `router.js`：前端页面/视图切换
- `workspace.js`：用户工作台
- `document.js`：分析与对比
- `chat.js`：智能问答
- `admin.js`：管理后台
- `state.js`：全局状态

## 6. 当前结构优点

1. 后端已经形成基本分层
2. API 模块边界清楚
3. OCR 与 AI 能力已经抽离到 `core/`
4. 文档目录已经开始独立建设
5. 项目整体仍然适合按单体架构继续收口

## 7. 当前结构问题

1. 身份体系仍带有匿名/演示特征
2. 前端还没有正式的门户与管理区结构
3. 缺少 `tests/` 目录
4. 缺少 `alembic/` 迁移目录
5. 缺少 `docker/` 或容器化配置文件
6. 前端脚本单文件过大
7. 运行数据与仓库数据的边界不够清晰

## 8. 第一版模块划分建议

### 8.1 前端模块边界
- 门户与认证：负责未登录访问入口
- 用户业务区：负责核心法律 AI 使用链路
- 管理后台：负责系统状态和治理能力

### 8.2 后端模块边界
- 认证模块：注册、登录、当前用户、角色校验
- 用户模块：工作台、历史、收藏
- 搜索模块：法条检索
- 文档模块：分析、对比、上传治理
- 聊天模块：会话与消息
- 管理模块：状态汇总、用户管理、记录管理

### 8.3 数据模块边界
- 用户主数据
- 分析/对比业务记录
- 聊天会话数据
- 收藏数据
- 可选系统配置数据

## 9. 后续推荐结构演进方向

### 本期建议新增
- `backend/app/api/admin.py`
- `tests/`
- `alembic/`
- `backend/scripts/`

### 本期建议逐步调整
- 将 `user.py` 从“匿名建档 + 用户功能”收口成“注册登录 + 用户工作台”
- 将前端单页入口重组为“门户 + app + admin”三段视图
- 将系统状态相关聚合查询沉淀为后台专用接口

## 10. 目录职责结论

当前仓库结构总体仍然是可演进的。第一版最正确的策略不是推翻项目，而是：
- 在现有单体架构上补齐正式系统外壳
- 用 `user/admin` 角色收口权限模型
- 用门户、登录注册、用户区、管理区重组前端结构
- 用新增 `admin` API 和正式用户模型补齐后台治理能力

这条路线改动集中、风险可控，也最符合当前三个月交付目标。
