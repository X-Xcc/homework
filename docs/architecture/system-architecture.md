# 系统架构设计文档

## 1. 文档目的

说明“法律 AI”项目在第一版正式交付范围内的整体架构、角色边界、页面结构、关键数据流与后续工程化治理方向，为前后端实现、数据库迁移、测试与部署提供统一设计基线。

---

## 2. 系统概览

- 项目名称：法律 AI - 智能法律顾问系统
- 当前目标版本：V1 校园/院内交付版
- 架构形态：FastAPI 单体后端 + 原生前端单页应用 + PostgreSQL（目标）
- 认证方式：本地账号密码登录
- 角色边界：`user`、`admin`
- 访问方式：未登录先进入系统门户，登录后按角色进入对应工作区
- 核心能力：系统门户、用户注册登录、法条检索、文档分析、文档对比、智能问答、历史记录、收藏、管理员系统状态与治理能力

---

## 3. 总体架构

### 3.1 逻辑分层
- 前端层：提供系统门户、登录注册、用户工作台、管理员后台等页面交互
- API 层：通过 FastAPI 对外暴露认证、搜索、文档、聊天、用户、管理等接口
- 业务服务层：负责法条检索、文档解析、AI 分析、聊天、收藏、统计汇总等业务逻辑
- 数据访问层：通过 SQLAlchemy Async 访问 PostgreSQL，管理用户、分析记录、聊天记录、收藏与系统配置
- AI/OCR 集成层：封装 MiMo、OCR 主备引擎、向量检索等外部能力
- 存储层：PostgreSQL、向量库目录、上传目录、静态法条/模板数据

### 3.2 部署形态
- 浏览器访问统一入口 `/`
- FastAPI 同时提供页面静态资源和 API 服务
- 应用以内聚单体模式部署，避免在本期引入微服务拆分
- 正式环境目标使用 PostgreSQL，开发期允许保留本地 SQLite 过渡，但不再作为最终交付形态

### 3.3 角色与访问分区
- 公共区：`/`、`/login`、`/register`、`/help`
- 用户区：`/app/*`
- 管理区：`/admin/*`

角色访问原则：
- 未登录用户只能访问公共区
- `user` 登录后访问用户区，只能查看和操作自己的数据
- `admin` 登录后访问管理区，可查看全站数据和执行管理操作

## 4. 第一版页面与导航结构

### 4.1 公共区

#### 系统门户 `/`
目标：作为学校/院内正式系统入口，而不是原型演示首页。

建议模块：
- 顶部导航：系统名称、功能介绍、帮助、登录、注册
- Hero 区：系统定位、核心能力简介、立即登录/注册入口
- 核心能力展示：法条检索、文档分析、文档对比、智能问答
- 使用流程说明：注册、登录、上传、分析、查看结果
- 系统公告/状态摘要：可展示“系统运行正常”等简要状态
- 页脚：版权、联系方式、使用须知

#### 登录页 `/login`
- 字段：用户名/邮箱、密码
- 能力：登录、跳转注册、忘记密码（第一版可仅预留入口）
- 登录成功：按角色跳转到 `/app` 或 `/admin`

#### 注册页 `/register`
- 字段：用户名、邮箱、密码、确认密码
- 规则：用户名唯一、邮箱唯一、密码强度最小要求
- 第一版策略：开放注册，注册成功后可直接登录

#### 帮助页 `/help`
- 使用流程
- 支持文件类型
- 常见错误说明
- 隐私与使用提示

### 4.2 用户区 `/app`

#### 用户工作台 `/app`
建议作为登录后默认首页。

展示内容：
- 我的分析次数
- 我的问答次数
- 最近分析记录
- 最近对比记录
- 最近聊天会话
- 常用入口卡片：法条检索、上传分析、文档对比、智能问答

#### 法条检索 `/app/search`
- 关键词搜索
- 法条详情查看
- 相关法条/相似法条（可保留当前能力）

#### 文档分析 `/app/analyze`
- 上传文档
- 展示分析进度/状态
- 返回风险项、总结、评分

#### 文档对比 `/app/compare`
- 上传两份文档
- 返回差异摘要与差异项

#### 智能问答 `/app/chat`
- 会话列表
- 新建会话
- 问答消息区
- 历史消息回看

#### 历史记录 `/app/history`
- 聚合显示分析、对比、聊天历史
- 支持按类型筛选

#### 收藏 `/app/favorites`
- 收藏法条/分析结果/模板
- 支持取消收藏

### 4.3 管理区 `/admin`

#### 系统状态仪表盘 `/admin`
第一版重点不是复杂 BI，而是稳定的系统状态总览。

建议看板：
- 系统运行状态
- 用户总数
- 今日/累计分析数
- 今日/累计问答数
- 最近上传活动
- 最近错误/失败记录数量
- 数据库连接状态
- AI 服务调用状态

#### 用户管理 `/admin/users`
- 用户列表
- 搜索/筛选
- 查看用户基本信息
- 禁用/启用用户
- 查看用户活跃情况

#### 文档管理 `/admin/documents`
- 分析记录列表
- 对比记录列表
- 查看异常任务或失败任务
- 必要时支持删除无效记录

#### 分析记录管理 `/admin/records`
- 按时间、状态、用户筛选
- 查看风险结果摘要
- 查看失败原因

#### 系统配置/公告（可选预留）`/admin/settings`
- 第一版可只做页面预留，不强制落地完整功能

## 5. 核心模块说明

### 5.1 认证与授权
- 采用本地账号密码体系
- 密码必须加密存储，不允许明文保存
- 登录成功后返回受信会话（Session 或 Token）
- 后端统一解析当前用户身份与角色
- 接口按角色限制访问范围

### 5.2 用户模块
- 负责注册、登录、当前用户信息
- 负责用户工作台、历史记录、收藏列表
- `user` 数据访问必须按 `user_id` 限制

### 5.3 法条检索模块
- 加载法条静态数据
- 提供关键词检索、详情查看、相似法条搜索
- 第一版不扩展为全国法规平台，只做现有数据治理与体验优化

### 5.4 文档分析模块
- 接收上传文件
- 进行文本解析 / OCR
- 调用 AI 输出风险结果、摘要、评分
- 保存分析记录与状态

### 5.5 文档对比模块
- 接收双文件上传
- 解析两份文档
- 调用 AI 输出差异摘要与变更项
- 保存对比记录与状态

### 5.6 智能问答模块
- 创建会话
- 保存消息
- 调用 AI 生成答复
- 支持历史回看与会话管理

### 5.7 管理后台模块
- 汇总系统状态
- 治理用户、记录和异常任务
- 为答辩与验收提供“系统可管理”的正式观感

## 6. 关键数据流

### 6.1 注册与登录流程
1. 未登录用户进入系统门户
2. 用户进入注册页创建账号
3. 后端校验用户名/邮箱唯一性
4. 密码加密后写入用户表
5. 用户在登录页输入账号密码
6. 后端校验凭证并生成会话
7. 前端根据角色跳转到 `/app` 或 `/admin`

### 6.2 文档分析流程
1. `user` 在 `/app/analyze` 上传文档
2. 后端校验文件大小、类型和归属
3. 文档解析器提取文本，必要时触发 OCR
4. AI 分析器返回风险项、摘要、评分
5. 后端保存分析记录并更新状态
6. 前端展示分析结果并支持进入历史记录查看

### 6.3 文档对比流程
1. `user` 上传两份文档
2. 后端解析两份文档文本
3. AI 对比器输出差异摘要和差异项
4. 保存对比记录
5. 前端展示结果并纳入历史记录

### 6.4 智能问答流程
1. `user` 创建或进入聊天会话
2. 前端发送消息到后端
3. 后端拉取会话上下文并调用 AI
4. 返回答复并保存消息
5. 用户可在历史会话中继续追问

### 6.5 管理后台状态汇总流程
1. `admin` 进入 `/admin`
2. 后端聚合用户数、分析数、问答数、失败数、近期活动等指标
3. 通过一个或多个管理接口返回仪表盘数据
4. 前端展示系统状态看板

## 7. 外部依赖

| 依赖 | 用途 | 风险点 | 备注 |
|---|---|---|---|
| FastAPI | Web 框架 | 低 | 主体框架继续保留 |
| SQLAlchemy Async | ORM 与异步数据库访问 | 低 | 配合 PostgreSQL 使用 |
| PostgreSQL | 正式数据库 | 中 | 需要迁移与部署能力 |
| Alembic | 数据库迁移 | 低 | 本期必须补齐 |
| MiMo API | AI 分析/问答 | 中 | 需处理错误、超时、结构漂移 |
| PaddleOCR | 图片文本识别主引擎 | 中 | 部署较重 |
| Tesseract OCR | OCR 回退引擎 | 中 | 依赖系统安装 |
| ChromaDB | 向量检索 | 中 | 需验证部署稳定性 |

## 8. 当前架构问题与治理方向

### 当前问题
- 现有身份体系偏演示化，仍依赖伪身份头和匿名模型
- 前端当前更接近单一演示页，缺少门户、登录注册、用户区、管理区的正式分区
- 数据模型尚未完全贴合“自注册 + admin/user”边界
- 管理端能力缺失，无法体现系统状态与治理能力
- SQLite 和运行时补丁方式不适合作为正式交付底座

### 治理方向
- 统一为“系统门户 + 登录注册 + 用户区 + 管理区”结构
- 正式收敛角色为 `user` 与 `admin`
- 停止以匿名访客为正式身份模型
- 引入 PostgreSQL + Alembic 作为正式数据底座
- 在不推翻单体架构的前提下完成工程化补强

## 9. 后续演进建议

### 第一版必须完成
- 门户页、登录页、注册页落地
- `user` / `admin` 鉴权边界落地
- 用户工作台与管理员系统状态页落地
- 核心业务接口按真实登录用户身份收口

### 第二阶段可扩展
- 从 `user` 中继续细分教师/学生角色
- 增加审核注册、密码找回、邮件验证
- 增加更完整的管理员公告/配置能力
- 增加更细化的运维监控和 BI 统计

---

## 10. 架构结论

本项目第一版最合理的交付路径，不是继续堆叠演示功能，而是把现有法律 AI 能力放入一个正式系统骨架中：
- 前台有系统门户
- 用户可自注册
- 登录后按 `user` / `admin` 分流
- 用户侧关注业务使用
- 管理侧关注系统状态与治理

这条路线改动范围可控、实现风险较低，同时能显著提升项目的正式度、可验收性和可扩展性。
