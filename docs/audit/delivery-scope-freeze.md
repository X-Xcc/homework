# 交付范围冻结清单

## 1. 文档目的

明确本期三个月窗口内的必做范围、优化范围和明确不做范围，防止项目在执行过程中持续膨胀。

## 2. 本期交付目标

- 交付周期：12 周
- 目标版本：准企业级交付版本
- 核心导向：稳定、安全、可测试、可部署、可演示、可验收

## 3. 本期必须完成范围

| 模块 | 必须完成内容 | 验收标准 | 备注 |
|---|---|---|---|
| 法条搜索 | 支持法条检索、详情查看、基础检索体验优化 | 可稳定搜索并返回准确法条内容 | 保留现有主数据源 |
| 文档分析 | 支持上传文档并生成风险识别、总结、评分结果 | 合同/法律文档分析链路可完整演示 | 重点补强稳定性与错误处理 |
| 文档对比 | 支持上传两份文档并输出差异结果 | 对比结果能稳定返回摘要和差异项 | 重点补强上传链路与 AI 容错 |
| 智能问答 | 支持创建会话、发送消息、保留历史、查看会话 | 单轮与多轮对话可运行 | 重点补强会话治理与异常处理 |
| 模板库 | 支持模板浏览、分类筛选、详情查看 | 模板库功能在前端可用 | 只做治理，不扩业务量 |
| 用户工作台 / 历史 / 收藏 | 支持用户注册登录、进入系统、查看工作台统计、历史与收藏 | 用户侧核心工作台链路完整 | 采用正式账号身份，不再以匿名模式作为正式交付边界 |
| 正式数据库能力 | 从 SQLite 升级到 PostgreSQL，引入 Alembic | 新环境可用 PostgreSQL 启动，迁移可执行 | 企业级交付基础能力 |
| 认证鉴权能力 | 建立正式登录与鉴权边界 | 不再依赖伪身份头作为最终可信身份 | 企业级交付基础能力 |
| 上传与接口规范 | 上传安全、统一响应结构、统一异常处理 | 错误输出可控，上传链路更安全 | 企业级交付基础能力 |
| 测试能力 | 补充单元、接口、集成测试基础 | 至少覆盖核心链路并可自动运行 | 企业级交付基础能力 |
| 部署能力 | 容器化、基础 CI/CD、部署文档 | 可在新环境按文档完成部署 | 企业级交付基础能力 |
| 文档交付能力 | 输出架构、数据库、API、部署、测试、验收文档 | 可作为验收材料直接使用 | 企业级交付基础能力 |

## 4. 本期只优化不扩展范围

| 模块 | 当前保留内容 | 本期优化方向 | 不扩展的部分 |
|---|---|---|---|
| 前端交互 | 保留现有单页应用模式 | 拆分脚本、优化状态管理、改善交互与专业感 | 不做全面 Vue/React 重构 |
| 法条数据能力 | 保留当前刑法、民法典数据源 | 可补搜索体验和结果组织 | 不做全国法规超大规模扩库 |
| 模板库 | 保留现有 JSON 模板库 | 可优化分类、展示和调用体验 | 不做 CMS 化模板后台 |
| AI 分析能力 | 保留当前 MiMo 调用路线 | 增强容错、日志、结果稳定性 | 不做多模型编排平台 |
| OCR 能力 | 保留 PaddleOCR + Tesseract 双引擎 | 加强部署说明与回退稳定性 | 不做复杂 OCR 训练平台 |

## 5. 本期明确不做

| 想法/功能 | 不做原因 | 后续阶段建议 |
|---|---|---|
| 多租户架构 | 明显超出当前三个月交付窗口 | 二期再评估 |
| 企业审批流 / 法务流程引擎 | 属于全新业务系统 | 二期再评估 |
| RBAC 多角色后台管理系统 | 会显著扩大范围 | 先保留 `user` / `admin` 两类基础角色边界 |
| 全量前端框架迁移 | 风险高、收益滞后 | 后续重构期评估 |
| 微服务拆分 | 当前单体完全够用，拆分风险大 | 暂不考虑 |
| 消息队列 / 异步任务平台重构 | 当前阶段不是交付瓶颈 | 可在二期按压力评估 |
| 云���生全家桶（K8s、服务网格等） | 与项目体量不匹配 | 不纳入本期 |
| 企业知识库/私有法务大模型训练 | 超出当前能力边界 | 后续研究方向 |
| 移动端 / 小程序独立版本 | 会形成第二套前端交付面 | 本期不做 |

## 6. 新增需求准入规则

只有满足以下至少一项的需求，才允许进入本期：

- 直接提升最终验收质量
- 直接修复核心安全或稳定性问题
- 明显降低交付风险
- 是当前核心业务链路不可缺少的一环

以下需求默认不进入本期：

- 只是“更高级”但不提升交付质量
- 只是“以后可能有用”
- 会显著拉高重构风险
- 会拖慢测试、部署、文档与验收节奏
- 需要引入新的大型技术栈或第二套系统

## 7. 本期交付的一句话定义

在保留现有法律 AI 核心业务能力的前提下，把项目从“可演示原型”升级为“可部署、可测试、可验收的准企业级系统”。

## 8. 本期不变的核心路线

1. 保持 FastAPI 单体架构作为主干
2. 保持原生前端为主，不进行高风险全面重构
3. 优先补工程能力，不优先扩新功能
4. 所有技术选择优先服务三个月内稳定交付

## 9. 范围冻结结论

当前项目已经具备足够完整的业务链路，本期成功的关键不在于“做更多”，而在于“做扎实”。

因此本期范围冻结结论为：
- 核心业务功能保留并稳定化
- 企业级基础能力必须补齐
- 非必要创新、重构和功能扩张一律后置
